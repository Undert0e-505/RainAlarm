# Rain Alarm

## About

Rain Alarm 0.3.1 is a clean-room, open-source Android app for a simple question: **when will rain reach my selected place?** Now shows a place-specific rain outlook; Radar lets you inspect the source imagery and its available time window. The app does not contain the retired RainToday app, its native library, artwork, credentials or assets. Research material under `Research/RainToday` is development-only and is never packaged.

Download the [v0.3.1 signed release](https://github.com/Undert0e-505/RainAlarm/releases/tag/v0.3.1) and read its [release notes](docs/releases/v0.3.1.md) before installing. Rain Alarm is an experimental weather aid, not a safety-critical warning service.

The launcher artwork is the project owner's supplied Android icon pack, included as density-specific legacy and adaptive PNG resources under the project's MIT license. The supplied Play Store image is in `artwork/play_store_icon_512.png`. Notifications use a separate white-on-transparent droplet/bell small icon, not the launcher background.

## First launch and defaults

A fresh install selects **Current location** as both the active and startup place. It requests foreground location permission once; until a fresh fix exists, Now/Radar say location is unavailable rather than using placeholder coordinates or silently forecasting for London. Approximate location remains usable as an honestly labelled provisional Current fix, but navigation-style Follow requires Android's Precise location choice. On Android 13+, a notification-permission request follows the location request if needed. Declining either request does not trigger repeated dialogs; Current can be retried from the place switcher and notifications from Settings. Previously stored places and explicit settings are preserved on upgrade.

The unset defaults are Rain Notification **on when permission allows**, all five Now weather indicators visible, radar playback **2×**, MeteoGroup as the pinned preferred radar provider, and dark app/dark map. Radar playback still starts **paused**. Settings can pin a different preferred provider without changing it merely because the selected place needs a fallback; the row also shows selected-place availability and the provider currently in use when it differs. Settings also controls speed, app/map appearance, a shared **Coverage mask darkness** from No mask to Dark, independent Compass-card and Graph-card appearance (each follows the app by default), visible weather indicators, alert toggle and default startup place. The mask strength defaults to 50%, producing 45%/42%/40% effective opacity on Dark/Slate/Light maps; its maximum produces 90%/84%/80% opacity while retaining map context. It changes only the unknown/outside-coverage scrim used by every provider. When RainViewer is explicitly preferred, the additional **Show likely snow** switch is available and defaults off. Radar's connected Wind/Lightning/Clouds controls persist each layer independently; initially all three are off. Settings' information area also shows the installed app version.

## Features

### Now

- The selected place is a centred title above a compact, non-scrolling compass/status card, with a nearby place-switch icon on its right. The card shows rain status or ETA, provider/source age and forecast coverage. The switcher offers saved places and virtual Current location; refresh shows progress and an updated/error result while retaining a valid same-place forecast when possible.
- The compass keeps geographic North up with 24sp N/E/S/W labels. Its precipitation-direction indicator is one outlined circular droplet path with a 90° outward tip and a translucent halo. Rain uses the supplied translucent droplet texture on both pointer and centre disc; RainViewer likely-snow uses a transparent snowflake/crystal texture over the matching icy severity colour. Dry forecasts use neither texture. Pointer and centre disc share a colour based on the strongest available forecast-envelope severity, even when direction is unavailable and only the disc can be shown. The centre shows **Now**, minutes until arrival plus “min”, or fresh model temperature when no incoming precipitation is predicted. If direction is unavailable, it is not invented.
- The centre disc uses the same intensity colour as a visible precipitation pointer. When precipitation is happening or approaching, the selected translucent rain or likely-snow texture sits over that colour so intensity remains visible. Dry temperature keeps a plain branded-blue disc. Centre text is opaque white with a subtle dark edge for contrast on pale precipitation colours. The compact settled disc fits an ordinary-phone main label—including temperature when no precipitation is expected—targeting 48sp. On entry or a place change, pointer travel, centre text/disc shrink and graph reveal share one one-second animation; a background refresh does not replay it. Disabling Android animations makes the effect immediate.
- A one-minute intensity series reaches **up to** the next 60 minutes, never beyond actual source coverage. The chart has three full-height Light/Medium/Severe bands, an average curve and a min/max envelope. Its baseline is the wet threshold, not raw zero intensity. The vertical Now axis aligns with the coloured bands' left edge; the available forecast fills the plot width through its real last minute, without an artificial +60 label or blank tail. Time ticks mark local ten-minute clock boundaries within that domain. Tap the plot (not the severity labels) to open Radar, paused at the corresponding continuous chart time. If the radar session cannot represent it, Radar says so and uses its normal entry time. The compact layout gives the plot usable height without shrinking the compass or other text.
- The lower card corners show local 24-hour sunrise/sunset and a compact two-column readout of selected-place Open-Meteo model **Temp, Pressure, Humidity, UV and Wind** (speed plus meteorological *from* direction). All five indicators are visible by default and individually hideable in Settings. Stale/missing facts remain unavailable rather than guessed.
- Returning from another tab to Now makes one fresh forecast/point-weather attempt, including a quick return; startup and repeat taps do not double-load. Manual refresh requests a fresh attempt. Forecast updates during that visit do not restart the entry animation.

### Radar and map layers

- The North-up MapLibre/OpenFreeMap map opens around the selected place at roughly a 20-mile horizontal span. You can pan and zoom beyond the radar's native pixel resolution; that overscales existing data, **not** new meteorological detail. A session caches its complete regional imagery until the screen is left, and the map keeps that regional tier at every zoom rather than replacing it with the selected-point analysis tile; pan/zoom therefore neither drops sibling segments nor downloads new regional crops. For all five MeteoGroup feeds, a style-aware scrim darkens map space outside a versioned nominal radar-range envelope. Each envelope is an offline-generated geodesic union of documented national radar-site ranges, clipped to that feed's exact native source-raster footprint; UK/Ireland retains its unchanged established UK, Jersey, Dublin and Shannon geometry, while Netherlands/Benelux, Germany, France and Switzerland use explicitly nominal national-network approximations because DTN publishes neither composite membership nor validity masks. These envelopes show fixed structural reach, not live availability, terrain, beam blockage, outage or guaranteed DTN inputs. OPERA uses the latest composite's no-data field inside its fixed European raster, and RainViewer uses its published coverage mask; both are aligned to the same cached regional raster plan and darken space outside the loaded footprint. Their in-footprint alpha mask and small outside bands use one raster compositing path, tint and the same user-controlled darkness, avoiding a rectangular shade change when zoomed out. No mask is fully transparent; Dark remains translucent enough to retain map context. Changing it replaces only the scrim layer without reloading weather data or resetting camera/timeline. If any mask cannot be obtained or represented safely it fails open rather than darkening the world. The scrim tracks the map below radar, ancillary layers, marker, controls, notices and attribution. The regional GLES renderer lazily uploads at most three radar/velocity frame pairs and has a visible static fallback on renderer failure.
- The map blends neighbouring observation and provider-forecast frames continuously using a clean-room symmetric velocity warp and hardware-linear source sampling. Its regional colour transfer is a translucent white/cyan/blue-to-deep-blue adaptation for a dark map; it does not synthesize higher-resolution rain. The continuous slider scrubs without snapping, with real-time observation/forecast distinction and 30-minute clock ticks. Playback loops at the selected 0.5×, 1×, 2× or 4× speed; the initial state is paused. A same-place refresh preserves whether playback was running, while direct slider scrubbing or opening a chart-selected time deliberately pauses it.
- The map remembers camera zoom/pan across tabs and sessions. A newly selected place is centred exactly while retaining the current radar zoom; refresh or session replacement for the same selection retains the exact pan and zoom. Radar's centred place title shares Now's size and position; a center-on-selected button and place switcher sit close to either side. The center button preserves zoom and selection. For virtual Current location, one app-wide foreground engine uses Google Play services fused high-accuracy fixes when available and framework GPS as fallback. Ordinary Current targets a battery-conscious five-second interval; the opt-in Follow control requests precise roughly one-second fixes, smoothly supersedes each camera move at the current zoom, and stays north-up. A real pan/zoom pauses Follow; tapping it again recentres to the latest accepted accurate fix. Approximate or weak fixes never masquerade as navigation quality. Follow is not persisted and keeps the screen on only while Radar is visible, Current is selected, Follow is active and the activity is foreground. Follow adds no background-location request, foreground service, wake lock or ongoing notification; its screen-on scope uses the visible activity view. The device-location control requests a fresh fix without blanking a still-fresh map. Refresh reloads the active radar session and every enabled ancillary layer while retaining the camera. Long-press map save remains available.
- While visible Follow is active, one cadence-aware coordinator quietly checks each source near its next expected publication rather than using unrelated fixed timers. Radar cadence is inferred from recent observations (with provider-specific fallback); EUMETSAT Clouds/Lightning use their advertised cadence; Wind and point weather align to 15-minute model steps. Checks wait a 45-second publication grace and unchanged/failed results retry after 1, 2 and then at most 5 minutes, with one request in flight per stream. Only enabled map layers poll. When an automatic radar check installs a refreshed same-place session, active playback continues through the handoff instead of returning to paused. Manual Refresh uses the same playback-preserving handoff while force-checking radar/Now, point weather and enabled layers and rebasing the schedule. Leaving Radar, stopping Follow, selecting a saved place or backgrounding the app pauses all automatic checks while preserving visible data and caches.
- Slow connections have finite provider-aware session deadlines. A map load has a 110-second total ceiling and a point-analysis load an 80-second ceiling; within that total, MeteoGroup, OPERA and RainViewer each receive bounded attempts rather than multiplying timeouts without limit. An explicit OPERA session gets a real 70-second map / 45-second analysis attempt, while OPERA after a failed MeteoGroup attempt receives the remaining bounded fallback window. Now has a 95-second overall ceiling. A timeout is shown as `Radar unavailable`; the existing Refresh control retries it, and it is never treated as a dry forecast. As soon as a selected coordinate exists, initial loading uses the real interactive basemap with compact bottom-right `Radar loading` progress and a stable timeline footprint, without exposing imagery from an earlier provider. An existing map/radar session remains visible during a same-place replacement attempt.
- Three connected 48dp map segments on a second toolbar row independently toggle the persisted **Wind**, **Lightning** and **Clouds** layers, so any combination—including all three—can be shown. Wind requests one bounded 15-minute Open-Meteo model series for a 5×5 grid over the *visible viewport* after a settled pan/zoom, then follows the radar cursor without per-frame network calls. The queue remains at `Wind loading` while MapLibre establishes the viewport and throughout a weak-connection recovery window. Retryable fast failures are retried at roughly 15, 30 and 45 seconds under a 55-second ceiling, rather than immediately declaring the grid unavailable. Any early nonretryable failure is recorded internally but does not shorten the same presentation grace: only a stable-viewport generation that reaches its full 55 seconds without a usable grid becomes `Wind unavailable`. A safe same-viewport grid stays visible during replacement, and obsolete pan/zoom generations cannot replace the latest result. The visible nine arrows form a 3×3 grid at the quarter, centre and three-quarter positions while one offscreen sample row/column remains on each side for coverage. Fifteen-minute wind is native in supported regions and interpolated from hourly model values elsewhere. Settings offers a Wind-only persistent arrow-size slider with a live preview whenever Wind is enabled. The arrows are unlabeled; the separately fetched current selected-place wind speed/*from* direction remains right-aligned beneath the segment group while enabled, including while the grid itself loads. Lightning displays EUMETSAT accumulated satellite flash **areas**, not individual ground strikes. Clouds automatically uses MTG Cloud Type RGB by day and Fog / Low Clouds RGB by night, with a deterministic coordinate/time fallback when selected-place daylight data is stale or missing. Over the observed radar timeline, Lightning advances at its advertised 5-minute cadence and Clouds at their 10-minute cadence; both choose the latest available observation at or before the cursor and hold their latest real observation through forecast time rather than inventing satellite forecasts. Each enabled satellite layer downloads and validates its complete finite set of unique observed regional PNG frames before showing any of that set. The `n/N` counter is that provider-independent set of unique satellite frames; `N` can legitimately differ between radar providers because their observed timeline windows have different start times and lengths, not because Clouds downloads a duplicate provider-specific set. Downloads share a two-request limit (hard maximum three), and the consolidated bottom-right queue reports `Clouds loading n/N` or `Lightning loading n/N`; Clouds and Lightning complete independently, and an already visible complete set remains in place while a refreshed set loads. Exact product/time/region requests reuse an app-owned atomic 128 MiB compressed-image LRU cache on loops, while MapLibre keeps a separate 64 MiB ambient cache for the base map (about 192 MiB total intended disk budget). Only the active bitmap, a pending replacement and a brief retiring source are decoded/live; the complete animation remains compressed on disk. Frame changes overlap until a post-reveal fully rendered callback proves the new bitmap was composited. Changing Clouds does not rebuild Lightning or vice versa. The alternate cloud product is tried if the preferred one fails. Clouds renders below Lightning; the satellite imagery shows cloud structures or fog/low cloud and does not prove surface fog. Expired Wind/Clouds/Lightning data starts one automatic replacement request per source identity; the queue says only `<Data> loading` while replacement runs and `<Data> unavailable` if it cannot be replaced, without exposing provider/freshness diagnostics.
- Satellite requests are constrained to a place-owned operating region: British Isles is preferred, followed by Europe, overlapping North America East/West definitions, then a bounded local fallback. Each region adds approximately 200 km around its inner selection footprint and stays fixed when the camera pans. EUMETSAT bounds are intersected with that outer footprint. Every frame is one transparent, aspect-preserving regional WMS image no larger than 1024px whose projected BBOX is exactly that intersection; the same image is georeferenced at every map zoom, so world view never requests a global satellite disk and close zoom deliberately overscales the fixed regional source rather than downloading a new tile set. Pan/zoom within the selected region does not restart preparation or make new satellite requests, and panning outside simply reveals no satellite pixels beyond the rectangle.
- Radar Refresh starts a new ancillary-layer generation. When Clouds is enabled it bypasses the five-minute EUMETSAT metadata/probe cache and freshly discovers and probes both daytime Cloud Type and nighttime Fog / Low Clouds; repeated or rapid taps never purge downloaded frames, and only the latest refresh generation may publish a result. Exact product/time/region PNG identities are immutable within the session, so valid files in the atomic 128 MiB LRU are reused and only missing, corrupt or evicted frames download. Downloads use a global two-request limit (hard maximum three), up to three attempts, a five-second connection timeout and a twenty-second read timeout. Clouds accepts provider metadata up to one hour old, performs no acquisition while disabled, and holds the latest observation throughout radar forecast time rather than inventing cloud forecasts.
- One compact bottom-right queue is authoritative for operational state, in deterministic Location, Radar, Wind, Clouds, Lightning order. Its public vocabulary is only `<Data> loading` (with `n/N` when useful) or `<Data> unavailable`; internal download, validation, render, source and freshness diagnostics do not leak into the UI. Location acquisition/failure uses `Location loading`/`Location unavailable` there, while the bottom-left rail is reserved for map/style/renderer/chart notices. A previous complete satellite set stays visible during replacement whenever possible. Manual Refresh immediately retries Radar and every enabled layer with fresh generations while disabled layers remain idle; the current-location control immediately changes a location failure back to loading while it retries.

### Places, providers and alerts

- Search, save, rename, pin, delete and select multiple places in Places. One explicit search submits ordinary text to both Open-Meteo/GeoNames for settlements and Photon for OpenStreetMap named places/POIs, then ranks and deduplicates the independent results. Only when those services have no strong name match, one bounded English Wikipedia/Wikimedia coordinates search supplements notable named places; straight and curly possessives share the same normalized query. A full UK postcode instead uses postcodes.io. Failure of one source does not discard useful results from another. Long-hold and drag saved rows to persist a custom order, or long-press Radar to save a coordinate. A deleted row disappears immediately and stays gone after storage confirms; a failed save restores it. Deleting the last saved place switches to virtual Current location without recreating London. A live Current selection consumes the same accepted fused/GPS foreground fix stream as Now and Radar, and uses the platform's locality name when available, falling back to one-decimal latitude and longitude. Every accepted Follow fix moves only the marker/camera; weather analysis and reverse geocoding move on a bounded anchor (at least 1 km, or after two minutes with at least 250 m), with an immediate first fix and regional-boundary correction. This avoids weather/network work once per second. Live coordinates stay in process memory unless **Save current location** is explicitly pressed; that action creates and selects a normal saved place which can then be renamed, reordered, pinned, deleted or used at startup. When a fresh fix is missing, the existing current-location control requests it again; foreground refresh can recover a stationary device without saving its coordinates. Settings chooses a *default startup place* independently from the active selection; a deleted saved default falls back safely.
- MeteoGroup/DTN regional radar is the initial preferred provider where one of its five configured feeds covers the selected coordinate. It supplies map observations, velocity textures and provider forecast frames. For regional Now/alerts, a separate location-selected **area profile** supplies average/minimum/maximum intensity when fresh; it is not exact pin-pixel truth. The raster point series is the fallback. **Open European / OPERA** is a selectable, credential-free EUMETNET OPERA composite across its fixed 3,800×4,400 km CIRRUS/LAEA product domain, independent of the five Meteo feed rectangles. It reads only required Cloud Optimized GeoTIFF blocks from the public 24-hour cache, preserves the source's ellipsoidal LAEA geometry and native 1 km data, and derives both regional map and selected-place detail from the same observations. OPERA supplies observations, not provider forecasts: future `Estimate` frames, Now and alerts use the app's confidence-gated motion analysis and remain unavailable when that evidence is insufficient.
- The filled pin in Settings is a global preferred provider, not a promise that it serves every saved or live location. Each place/session tries that provider first when geographically eligible, then the remaining eligible providers in regional MeteoGroup, European OPERA and worldwide RainViewer quality order. A fallback never moves the pin; manual Refresh retries the preference. A concise temporary message beside the map information icon reports a genuine location/provider fallback or no-coverage result once, without adding a persistent provider badge. Temporary network, publication and decode failures remain separate from hard geographic capability, and current OPERA no-data gaps never shrink its fixed domain or make selection flap.
- RainViewer RGB is decoded from its published Universal Blue reflectivity colours into the same Rain Alarm intensity palette and animation treatment; PNG alpha is transparency, never precipitation strength or proof of radar coverage. Its regional tier is aligned to the corresponding MeteoGroup area footprint where available and otherwise remains centred on the selected place; its detail tier remains for Now/alerts rather than replacing the map at close zoom. The published coverage mask is requested once per session using the same screen raster plan (or the detail plan for point analysis). A fresh tile with no above-threshold echoes is reported as a clear next hour without inventing a direction only when that mask confirms the selected point and substantially the whole retained tile are covered. Missing/stale/invalid coverage remains unknown and fails open visually. When RainViewer is explicitly preferred, optional **Show likely snow** requests its model-assisted snow colours and uses an icy lavender-to-indigo hue across Radar, Now, the graph and alert wording. It stays off when RainViewer is only a fallback and is not claimed for OPERA. RainViewer's future path prefers a confidence-gated local motion field and can use a separately confidence-gated broad translation when local motion is unavailable; both are estimates, not provider forecasts. An estimate stops at the downloaded coverage edge rather than treating unseen space as dry. The three providers are independent composites and can materially disagree about precipitation footprint, intensity and timing; the app calibrates presentation but never expands, shrinks or moves one provider's echoes to imitate another.
- Preferred-provider pins update immediately in Settings. Rapid changes are coalesced for 400 ms before persistence and selected-place radar analysis, so the last deliberate choice wins without starting a bitmap-heavy Now load for every intermediate tap. Manual refresh, place changes, startup and Radar-screen refresh keep their normal independent behavior.
- Rain Notification is for the **active selected place**, saved or live. It fires only when the available series says dry now but predicts rain within 60 minutes. Text includes the place, ETA and expected local start clock time. Duration and peak are included only when a complete rain episode ends inside the known prediction window. Each sent alert suppresses that place until its recorded forecast wet-window end plus a ten-minute grace period; later qualifying rain can alert again without requiring a full-clear forecast. WorkManager timing is inexact; saved-place alerts need no location permission, while live Current background checks skip without a lawful fresh foreground fix.

### Appearance

App appearance offers Dark, Light and Follow system. Map appearance offers Dark, Light, Follow system and Slate, with dark app/dark map defaults. Compass and Graph cards independently offer Dark, Light, Follow app and Slate; Follow app remains their default. Card Slate uses the same `#45516E` mid-dark base independently for each card. Follow system reacts to Android night-mode changes. Light map uses OpenFreeMap Liberty, Dark keeps the existing OpenFreeMap Dark style, and map Slate uses OpenFreeMap Fiord with dark map-control contrast. Dark and Slate lift text-bearing place, road, reference and water labels with style-specific colours and halos while leaving map icons, typography and hierarchy intact. Changing among map styles retains the radar session, camera, selected timeline position and overlays.

Radar is an experimental information aid, not a safety-critical warning service. A dry/no-alert state can result from missing, stale or uncertain data. Do not rely on it alone for weather safety decisions.

## Data, attribution and limits

MeteoGroup/DTN regional imagery covers only configured UK/Ireland, Germany, Benelux, France and Switzerland feeds. Manifest timestamps and forecast flags determine the map window, which may be shorter than phone time +60 if the most recent observation is delayed. The separate area profile used by Now/alerts also has its own freshness and horizon. Regional source images have fixed pixel dimensions (the UK feed is 583×767 over the whole region), so zooming cannot increase physical source resolution. OPERA covers its fixed pan-European CIRRUS composite domain at native 1 km resolution; it carries DBZH observations and a quality band but no provider forecast or snow type. RainViewer supplies observed radar coordinate imagery worldwide, while its separate published mask determines radar coverage at a location. OPERA and RainViewer motion fields and future paths are calculated locally and withheld when confidence is insufficient. RainViewer's “likely snow” channel is model-assisted precipitation typing, not an observation of surface snowfall. Intensity percentages are normalized reflectivity-derived display severity, **not** rainfall or snowfall rate in mm/h. Open-Meteo current weather is 15-minute weather-model output, not a live instrument reading; its free public API is subject to [noncommercial and attribution terms](https://open-meteo.com/en/terms). OPERA and EUMETSAT WMS data use CC BY 4.0 attribution. See [data sources and constraints](docs/DATA_SOURCES.md).

Map data © OpenStreetMap contributors, rendered via OpenFreeMap/OpenMapTiles; the map keeps MapLibre's compact native attribution control and provider details live in Settings under **About the data**. OpenFreeMap's [quick-start documentation](https://openfreemap.org/quick_start/) describes the public MapLibre styles and attribution. Regional radar is supplied by MeteoGroup/DTN; open European radar is EUMETNET OPERA Open Radar Data under CC BY 4.0; worldwide open radar is RainViewer; model weather is Open-Meteo under CC BY 4.0; and satellite layers are EUMETSAT under CC BY 4.0. Town search uses Open-Meteo/GeoNames, while named-place/POI search uses [Photon](https://photon.komoot.io/) over © OpenStreetMap contributors data and, only for weak primary matches, geocoded pages from [Wikipedia/Wikimedia](https://www.wikipedia.org/). Complete UK postcode lookup uses the free, no-auth [postcodes.io](https://postcodes.io/) API under its [published data licences](https://postcodes.io/docs/licences/), including OS OpenData terms and Ordnance Survey/Crown, Royal Mail and National Statistics database-right notices. This project sends no account, advertising, analytics or billing data and embeds no provider credentials. Network requests to data/map providers necessarily expose ordinary network metadata to those services; consult their terms and privacy policies for current details.

## Permissions and privacy

`INTERNET` loads maps, radar, search, weather models and optional satellite imagery. Ordinary non-postcode place text is sent in parallel to Open-Meteo for towns and Photon for OSM named places; if neither returns a strong name match, one sequential English Wikipedia/Wikimedia query may be sent for geocoded notable pages. Queries shaped as complete UK postcodes are sent only to postcodes.io for exact lookup. Search happens only on explicit submit, uses bounded results/timeouts and small in-process Photon/Wikimedia caches, and sends no API key. Enabling Wind sends a bounded 25-coordinate, active-session time-series request for the visible map viewport to Open-Meteo after camera idle; the selected-place weather/solar request sends only that selected coordinate. Enabling Lightning and/or Clouds loads EUMETSAT capabilities and the finite region-wide WMS animation images independently; leaving all three segments off loads no ancillary layer. Existing persisted Fog selections migrate in place to the equivalent Clouds segment. The regional Now/alert profile first sends selected coordinates to MeteoGroup's HTTPS area lookup, then sends the returned area ID to its chart service. That chart service currently requires plain HTTP because its HTTPS certificate fails hostname verification; Android permits cleartext only for that exact host. These requests send no device or account identifier. A fresh install selects virtual Current location (no coordinates stored), shows unavailable until a fresh fix, and requests foreground location permission once; denial leaves Current unavailable and a saved place can be selected. Foreground location uses Google Play services' fused provider where available, falling back to Android GPS; precise Follow increases location and screen power use only while visibly active. Live fixes and coordinates remain memory-only. Follow requests no background location, wake lock, foreground service or ongoing location notification; WorkManager retains its existing Android scheduling components for optional periodic rain alerts. On Android 13+, the app requests notification permission once after the location prompt if needed; denial leaves Rain Notification off with a permission-needed message, and Settings can retry. Existing selections and explicit settings survive upgrades. The fresh defaults are all five Now weather indicators and 2× radar playback. Saved places, preferred-provider/appearance/playback/default/metric/layer choices and alert state are stored locally. A legacy persisted current-location record is migrated to the virtual live selection without retaining its old coordinates; saved places remain intact.

## Build and test

The 0.3.3 app has version code 17, supports Android 8.0+ (min SDK 26), and compiles/targets SDK 37. Build requirements are JDK 21, Android SDK Platform 37, Build Tools 36.0.0, Android SDK command-line tools, and network access for first dependency resolution. Open the project in Android Studio or use the included Gradle wrapper. On Windows:

```powershell
$env:ANDROID_HOME='D:\path\to\android-sdk'
.\gradlew.bat :app:directDebugUnitTest :app:lintDebug :app:assembleDebug
```

The debug APK is `app/build/outputs/apk/debug/app-debug.apk`. Standard `:app:testDebugUnitTest` can be used in CI. On this particular development host, Java's AF_UNIX selector cannot start the Gradle test worker; the checked-in `:app:directDebugUnitTest` runs the same pure JVM tests via JUnitCore. If needed here, set `JAVA_TOOL_OPTIONS=-Djdk.net.unixdomain.tmpdir=Z:\rainalarm-no-socket-dir` before Gradle. That host workaround is not an Android runtime requirement.

The Windows [release helper](scripts/build-release.ps1) runs tests, lint, assemble and APK signature verification, then copies a versioned artifact to ignored `dist/` and prints size and SHA-256:

```powershell
.\scripts\build-release.ps1 -Mode Debug
```

### Locally signed release

Android release APKs need a private signing key ([Android's command-line signing guide](https://developer.android.com/build/building-cmdline)). This development host has one long-lived release key outside the repository, with its passphrase protected by the current Windows user's DPAPI profile. Repeat a local signed build with:

```powershell
.\scripts\build-signed-local.ps1 -WhatIf
.\scripts\build-signed-local.ps1
```

The helper runs tests, lint, minified release assembly and signature checks without publishing. It prints the artifact path and SHA-256; repeated builds keep prior APKs in ignored `dist/`. The existing `build-release.ps1 -Mode Release` path still accepts the four `RAIN_ALARM_SIGNING_*` environment variables from a private shell or CI secret store. No password belongs in command arguments, shell history, commits, logs, issue reports or screenshots. An unsigned `assembleRelease` alone is **not** a distributable.

Use the same signed-local helper for every phone-installable preview of an existing release installation: a debug-signed APK cannot update it in place. Keep previews local, give each shared-drive copy a unique filename, and verify the certificate, version and checksum. See the [project agent workflow](AGENTS.md) and [signing guide](docs/SIGNING.md); do not replace the established key if it is unavailable.

The owner confirmed off-machine backup of both the keystore and passphrase before the v0.1.0 publication. DPAPI alone is not a portable backup. See [local signing, certificate identity and backup instructions](docs/SIGNING.md). Version name/code live in `app/build.gradle.kts` and must be advanced deliberately for a public release.

### Optional publication

The public repository is [Undert0e-505/RainAlarm](https://github.com/Undert0e-505/RainAlarm). **Future builds are not tagged or published by default.** A maintainer with a clean tree, the original private signing key, a configured GitHub remote and authenticated `gh` may explicitly use `-Publish` with signed Release mode:

```powershell
.\scripts\build-release.ps1 -Mode Release -Publish -Remote origin -NotesFile .\docs\releases\v0.3.1.md -WhatIf
.\scripts\build-release.ps1 -Mode Release -Publish -Remote origin -NotesFile .\docs\releases\v0.3.1.md
```

`-WhatIf` previews without building or publishing; release signer variables are still checked. Actual publication checks Git root, clean tree, remote, `gh` authentication and local/remote tag/release collisions. It then makes annotated tag `v<version>`, pushes branch and tag without force, and creates a GitHub Release with the signed APK. If no notes file is supplied, GitHub generates notes. Use only after reviewing code, tests, device checks, permission disclosures and the exact artifact. A failed partial publication may leave a local or pushed tag; inspect it before retrying rather than forcing an overwrite.

## Contributing and testing

Small focused issues and pull requests are welcome. Preserve the clean-room boundary: do not copy proprietary RainToday source/native binaries/assets, ship provider credentials, or add undocumented endpoints. Include pure unit tests for decision/math changes, run the checks above, and describe device/API-level checks for UI, permissions and GLES changes. Physical-device testing should cover both providers, rapid scrubbing, light/dark app and map, short-screen layout, live fix denial/recovery, saved-place alerts, and foreground/background transitions. Forecast/alert behavior depends on live data; tests cannot guarantee future service availability.
